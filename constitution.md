# Todo In-Memory Python Console App Constitution

## Project Purpose

This constitution governs **Phase I only** of the Todo In-Memory Python Console App project.

**Goal**: Build a minimal, functional, console-based Todo application in Python that operates entirely in memory. The application enables users to manage tasks through a text-based terminal interface without any external persistence, web interfaces, or advanced features.

**Phase I Vision**: Deliver a working prototype that demonstrates core CRUD (Create, Read, Update, Delete) operations for todo tasks, validated through Spec-Driven Development principles and implemented exclusively via Claude Code.

---

## Phase I Scope

Phase I includes **exactly five features**, no more, no less:

1. **Add Task**: User can create a new todo task with a description
2. **Delete Task**: User can remove an existing task from the list
3. **Update Task**: User can modify the description of an existing task
4. **View Tasks**: User can display all tasks in a readable format
5. **Mark Task Complete/Incomplete**: User can toggle the completion status of a task

**Mandatory Constraints**:
- All data stored **in-memory only** (Python data structures: lists, dictionaries, objects)
- **Console-only interface** (text-based menu or prompt-driven interaction)
- **No persistence** (data lost when application exits)
- **Python 3.13+** as the target runtime

---

## Out-of-Scope Items (Phase I)

The following are **explicitly prohibited** in Phase I and MUST NOT appear in specifications, plans, or implementation:

### Persistence & Storage
- Databases (SQL, NoSQL, key-value stores)
- File-based persistence (JSON files, CSV, pickle, SQLite)
- Any form of data retention across application restarts

### User Interfaces
- Web interfaces (Flask, Django, FastAPI endpoints)
- GUI frameworks (Tkinter, PyQt, wxPython)
- Mobile applications
- Browser-based clients

### Advanced Features
- **Task priorities** (high/medium/low, numeric rankings)
- **Search or filtering** (by keyword, date, status)
- **Recurring tasks** (daily, weekly, scheduled events)
- **Categories or tags** (grouping, labeling, hierarchies)
- **Due dates or timestamps** (deadlines, creation dates, reminders)
- **Multi-user support** (user accounts, permissions, sharing)
- **Authentication** (login, passwords, sessions)
- **AI features** (natural language processing, recommendations, auto-categorization)
- **Sorting** (alphabetical, by completion, custom order)
- **Undo/redo** functionality
- **Task dependencies** (blockers, parent/child relationships)
- **Notifications** (email, push, alerts)
- **Import/export** capabilities
- **Logging** (beyond basic error messages to stderr)
- **Configuration files** or settings management

**Scope Enforcement**: Any specification or plan proposing out-of-scope features MUST be rejected during quality validation. The `todo-spec-auditor` agent is responsible for flagging scope violations.

## Spec-Driven Development (SDD) Rules

All functionality in Phase I MUST adhere to strict Spec-Driven Development principles:

### Rule 1: Specification First
- Every feature MUST have a written specification in `specs/<feature-name>/spec.md` **before** any implementation begins
- Specifications MUST include:
  - User stories in Given/When/Then format
  - Acceptance criteria (minimum 3 testable criteria per feature)
  - CLI command syntax and examples
  - Expected outputs and error messages
  - Edge cases

### Rule 2: No Manual Code Authoring
- **Developers MUST NOT write or edit source code manually**
- All production code MUST be generated by Claude Code based on specifications
- Direct edits to `.py` files in `src/` are prohibited

### Rule 3: Spec Refinement Over Code Patching
- If behavior is incorrect or incomplete, the specification MUST be updated first
- Claude Code regenerates implementation from the updated spec
- Never "quick fix" code directly; iterate on the spec until behavior is correct

### Rule 4: Validation Before Implementation
- Specifications MUST pass validation by the `todo-spec-auditor` agent before proceeding to planning
- Plans MUST pass validation by the `phase1-quality-orchestrator` agent before implementation begins
- Use `/sp.specify`, `/sp.plan`, and `/sp.tasks` workflow strictly

### Rule 5: Traceability
- Every code artifact MUST be traceable to a specific requirement in the spec
- Tasks in `tasks.md` MUST map to user stories and acceptance criteria
- Prompt History Records (PHRs) MUST be created for all specification and planning activities

## Python Coding Standards

All generated Python code MUST adhere to the following standards:

### Language & Runtime
- **Python Version**: 3.13+ (use modern syntax and standard library features)
- **Standard Library Only**: No external dependencies unless explicitly approved in spec (Phase I should require none)
- **Type Hints**: Use type hints where they improve clarity (optional but encouraged)

### Code Quality Principles

#### 1. Clear Naming
- **Functions/methods**: `snake_case`, intention-revealing names (e.g., `add_task`, `mark_task_complete`)
- **Classes**: `PascalCase`, noun-based names (e.g., `TodoList`, `Task`)
- **Constants**: `UPPER_CASE` (e.g., `MAX_TASKS`, `DEFAULT_STATUS`)
- **Avoid**: Abbreviations (`todo_mgr` → use `todo_manager`), single-letter names (except loop counters)

#### 2. Small, Focused Functions
- **Maximum function length**: 30 lines (guideline, not hard limit)
- **Single Responsibility**: Each function does one thing well
- **Function parameters**: Prefer ≤4 parameters; use data classes or dictionaries for more
- **Cyclomatic complexity**: Keep ≤10 (reduce nested conditionals and loops)

#### 3. Modular Structure
- **Separation of Concerns**:
  - CLI interface code separate from business logic
  - Business logic separate from data structures
  - Example structure:
    ```
    src/
    ├── models/        # Task, TodoList data structures
    ├── services/      # Business logic (add, delete, update, view)
    ├── cli/           # User interaction, menu, prompts
    └── main.py        # Application entry point
    ```

#### 4. In-Memory Data Structures
- **Allowed**: Python lists, dictionaries, sets, custom classes
- **Primary structure**: Use a simple list or dictionary to store tasks
- **Example**:
  ```python
  # Simple in-memory storage
  tasks = []  # List of Task objects

  # Or dictionary for ID-based access
  tasks = {}  # {task_id: Task}
  ```

#### 5. Clean Code Practices
- **Avoid magic numbers**: Use named constants
- **Avoid deep nesting**: Prefer early returns, guard clauses, extraction
- **Docstrings**: Include for public functions/classes (brief, clear purpose)
- **Comments**: Minimal; code should be self-explanatory (comment "why", not "what")

## Console Application Requirements

The application MUST run entirely in the terminal with text-based interaction:

### Interface Style
- **Menu-driven** or **prompt-driven** interaction (choose based on spec, prefer menu for clarity)
- Example menu:
  ```
  === Todo App ===
  1. Add Task
  2. Delete Task
  3. Update Task
  4. View Tasks
  5. Mark Task Complete/Incomplete
  6. Exit
  Enter choice:
  ```

### User Interaction
- **Input**: Use `input()` for user prompts; validate inputs before processing
- **Output**: Use `print()` for normal output to stdout
- **Errors**: Print error messages to stderr (use `sys.stderr.write()` or `print(..., file=sys.stderr)`)

### Output Clarity
- **Human-readable format**: Display tasks in a clear, scannable list
- Example:
  ```
  Tasks:
  1. [Incomplete] Write project spec
  2. [Complete] Set up Python environment
  3. [Incomplete] Implement add task feature
  ```
- **Feedback messages**: Confirm actions (e.g., "Task added successfully", "Task not found")

### Exit Behavior
- Provide explicit exit option (e.g., menu choice 6 or command "exit")
- Exit cleanly with return code 0 on normal termination
- Use non-zero exit codes for errors (e.g., 1 for invalid input, 2 for critical failure)

## Error Handling & Validation

The application MUST handle errors gracefully and never crash on invalid input:

### Input Validation
- **Validate all user inputs** before processing (e.g., task ID exists, choice is valid)
- **Reject invalid data** with clear error messages (e.g., "Invalid task ID: 99", "Choice must be 1-6")

### Error Messages
- **User-friendly**: Explain what went wrong and how to fix it
- **Example**: "Error: Task ID must be a number" (not "ValueError: invalid literal for int()")
- **Actionable**: "Please enter a number between 1 and 5" (tell user what to do next)

### Robust Handling
- **No crashes**: Application MUST NOT exit unexpectedly on bad input (wrap in try/except where appropriate)
- **Recovery**: Return to menu or prompt after error; allow user to retry
- **Edge cases**: Handle empty task lists, non-existent IDs, duplicate IDs gracefully

### Exit Codes
- **0**: Successful execution
- **1**: User input error (invalid choice, bad data)
- **2**: Application logic error (should be rare if SDD followed correctly)

```
│   ├── delete-task/
│   ├── update-task/
│   ├── view-tasks/
│   └── mark-complete/
│
├── history/                 # Prompt History Records (PHRs) and ADRs
│   ├── prompts/
│   │   ├── constitution/
│   │   ├── general/
│   │   └── <feature-name>/
│   └── adr/

├── .specify/               # SpecKit Plus templates and scripts
│   ├── memory/
│   │   └── constitution.md  # This file
│   ├── templates/
│   └── scripts/
│
├── .claude/                # Claude Code agents and skills
│   ├── agents/

│
├── README.md               # Project overview, setup instructions, usage
├── CLAUDE.md               # Claude Code rules and SDD workflow guidance

```

### File Naming Conventions
- **Python modules**: `snake_case.py` (e.g., `todo_service.py`, `task_model.py`)
- **Specs**: `spec.md`, `plan.md`, `tasks.md` (consistent naming)
- **PHRs**: `<ID>-<slug>.<stage>.prompt.md` (e.g., `001-create-constitution.constitution.prompt.md`)
- **ADRs**: `<ID>-<title>.md` (e.g., `001-use-list-for-task-storage.md`)

### Structure Enforcement
- Source code MUST reside in `src/` (not root, not subdirectories like `app/` or `lib/`)
- Specifications MUST reside in `specs/<feature-name>/` (not `docs/`, not `spec-history/`)
- README.md and CLAUDE.md MUST exist at repository root

**Note**: The user input specified `specs-history` folder, but standard SDD convention uses `specs/`. The structure above uses `specs/` for consistency with SpecKit Plus templates. If `specs-history/` is preferred, this can be amended, but requires updating templates.

Phase I is considered **complete** when ALL of the following criteria are met:

### Functional Completeness
1. ✅ All five features work correctly:
   - Add Task
   - Delete Task
   - Update Task
   - View Tasks
   - Mark Task Complete/Incomplete

2. ✅ Application runs successfully from command line:
   - Execute with `python src/main.py` (or equivalent entry point)
   - Menu or prompt displays correctly
   - User can perform all five operations without crashes

3. ✅ All acceptance criteria from specs are satisfied:
   - Each feature's `spec.md` acceptance criteria validated
   - Edge cases handled as specified
   - Error messages match spec expectations

### Process Compliance
4. ✅ All code generated via spec-driven workflows:
   - No manually authored code in `src/`
   - All features have corresponding specs in `specs/<feature>/`
   - PHRs exist for all specification and planning activities

5. ✅ Quality gates passed:
   - Specifications validated by `todo-spec-auditor` (no FAIL status)
   - Plans validated by `phase1-quality-orchestrator` (GREEN status)
   - Code reviewed by `todo-code-quality-agent` (no CRITICAL issues)

### Documentation Completeness
6. ✅ README.md exists and includes:
   - Project description
   - Setup instructions (Python version, how to run)
   - Usage examples (how to use the five features)

7. ✅ CLAUDE.md exists and includes:
   - SDD workflow rules
   - Claude Code usage instructions
   - Reference to this constitution

### No Scope Creep
8. ✅ No out-of-scope features implemented:
   - No persistence, web UI, AI, or advanced features
